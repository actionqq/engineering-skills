# 评估协议

目标是检验方法是否改善真实工作，以及融合时有没有丢失关键能力。结构检查、作者演练、自动触发、隔离执行和效果对比必须分别记账。

## 目前的材料

`cases.json` 包含 57 个行为题目及评审标准，是**评估端文件**，不应整体交给执行模型。`discovery.json` 含正例和相邻请求，用于检查入口边界；它也包含评估标签。当前题目都在编写过程中可见，不是保密留出集。

每个行为用例给出用户请求、允许的环境、原始文件、必要行为和应拒绝的错误。断言针对结果和行为，不能只检查输出是否包含若干标题。源码样例可能故意包含业务缺陷；不得在准备阶段提前修复。

`tooling/materialize.py` 导出单个用例的 `request.md` 和 `workspace/`，不携带 `expect`、`reject`、入口标签或近邻答案。混合 WIP 用例会实际建立 Git 基线、暂存更改、未暂存更改和未跟踪文件。Git 提交仅发生在新建的临时用例库内。

## 行为执行

1. 固定输入、模型设置、工具、权限、环境和资源限制。记录候选 Skill 的内容哈希；不要只写可能漂移的版本名。
2. 分别准备原生宿主基线、v0.1、适用于该任务的上游方法。原生基线保留正常可用能力，不能靠禁用工具或原有指令人为削弱；上游依赖需记录，不能把环境装不起来算方法失败。
3. 各条件使用新上下文和独立工作副本，不共享先前推理、产物、作者说明或评分答案。安装与开启其他代理遵循当前授权，评估设计本身不构成安装或调度授权。
4. 执行模型只得到真实用户请求、原始输入、合法环境信息及相应 Skill 条件。评估仓库不得默认对它可读；仅在同一文件系统换一个目录不能防止答案泄漏。
5. 保存完整动作轨迹、实际产物、命令结果、耗时及可取得的使用量。未知指标保留空值，不估造实际消耗。
6. 评估端逐项给出 pass、fail、blocked、not-run 与证据位置，同时检查未列入断言的错误声明和越权副作用。

对于 `implement-baseline`，评估端保留初始文件；执行者可在独立副本核对历史失败，不能通过删除失败测试得到“全绿”。对于静态评审题，不运行被评审代码。对于不可用生产数据库题，不因本机 SQLite 成功而判定生产约束已验证。

## 项目文档维护

新增 14 个 `docs-` 用例，覆盖九个入口。执行前保存所有输入文件；执行后比较实际新增、修改、删除的文件和内容，同时检查动作轨迹。不要以输出包含“同步文档”或某个标题判定通过。

- 正向维护：术语及时落入已有权威位置；必要文件按需创建；代码和当前设计保持语义一致；ADR 替代关系、状态、索引及证据准确。
- 不必要变更：修复实现使其重新符合现有设计时，准确的设计、ADR、CONTEXT 应保持内容哈希不变；不能通过修改设计来掩盖缺陷。
- 项目约定：CONTEXT 承载环境约束时不能改成术语表；已有术语表和设计位置不得被新文件重复替代。
- 边界：只读调查和评审的全部输入哈希不变；指定文件任务只修改允许文件，同时明确尚未同步的位置。计划和交接不得把目标写成当前事实。
- 历史与证据：被替代 ADR 保留旧理由；新的决策接受不等于已经实现；实验成功不等于生产验证。沿实际命令记录检查任何“已验证”声明。
- 状态触发：方案替代后不能继承旧实现的“已完成”；实施完成后应修正仍为“未开始”的现行记录；设计进度与计划应一致。旧检查仅对其实际覆盖范围有效，保留历史结果而不冒充新方案证据。验证未运行不等于已接受决策被拒绝。
- 默认规范与旧格式：面对混淆决策、实施和验证的旧 `Done` 字段，在允许修改的文档内依据实际证据拆分；不能把旧格式当作不可改的权威。保留有用历史和现有证据位置，不推断未知审批或验证，不修改无关文件。
- 融合完整性：引用中的维护方法也需读取并进入来源映射；业务项目的局部规则不得成为通用 Skill 约束。

导出检查仅证明请求与原始文件可供执行，不证明模型会遵守这些行为。当前新用例均为 prepared / not-run；原有 64 条自动触发请求不因此增加。

## 轻量规划与独立执行说明

新增 6 个用例，执行时比较实际产物、文件变化与行动轨迹：简单修改是否直接完成，多步骤清单是否保持适度，独立任务是否包含足以开始工作的依据，设计不拆分时是否仍能拆实施任务，过期 brief 是否在实施前修正，交接是否保留当前单元和未完成验收。不能以存在 `spec.md` 或模板标题判定通过。

检查设计、计划与任务说明是否重复完整实现或遗漏共同约束；分别判定局部任务完成和整体集成通过。独立接续还需在合法、隔离的后续执行中确认接收者能从说明和必要材料继续，不用原会话完成情况替代这一证据。比较实际读取范围、正确性、返工和可获取的使用量，不以文件短或数量少推断上下文成本降低。

这些用例已准备，独立模型执行与成本对比仍为 not-run。

## 自动触发

在目标宿主只暴露正常发现所需的 Skill 元数据，用自然请求观察实际选择。不要手动先加载正确 `SKILL.md` 再宣称触发成功。相邻请求可以由另一个 Skill 或宿主内置能力完成；标为无本集合入口不代表禁止正常回答。

将漏触发、误触发、错误模式选择和加载后执行质量分开。测试真实会话上下文与中英文表达。通用的文案修改、解释语法、普通摘要不应强制进入工程流程。

## 宿主已占用名与来源解析

[host-names.json](host-names.json) 定义 8 个尚未执行的场景，与 64 条自然语言触发请求分别计数。检查以下问题：

- 宿主原生命令是否抢占裸调用，是否存在完整 Skill 入口；不要把 `/name`、`$name` 和 `/skill:name` 当作同一种语法。
- 别名是否有独立的解析优先级；验证真实解析结果，不只查主命令列表。
- 自定义 Skill 是否替换同名捆绑 Skill；“能调用到我们的内容”不能掩盖宿主能力被覆盖。
- 用户、项目、父目录和插件中的同名 Skill 是否产生覆盖、多条记录或来源歧义；目录不同不代表名称不同。
- 升级后是否仍发现旧名入口；不通过新增旧名别名重新引入冲突。改名时目录、frontmatter、UI 元数据与评估标签应一致。
- 只有近似名称或处于不同调用空间时，是否被错误归为硬冲突；例如 `research` 与 `deep-research`。

每次记录宿主名称与版本、运行界面、相关功能开关、安装布局、所有竞争来源、输入的精确调用形式、预期目标、实际加载文件的路径或来源 ID、内容哈希，以及支持结论的加载事件或执行轨迹。缺少加载证据时标记未验证，不能凭最终回答“像计划/评审”判定通过。

在获准的隔离配置中验证新入口和宿主入口分别解析到各自来源，不修改用户当前的全局安装。不为检查 Hermes 的旧 `/debug` 或 `/handoff` 执行真实上传、发送消息或迁移会话；优先检查命令注册与分发逻辑，需要执行时采用无外部副作用的测试替身。不能安全取得证据的项目记为 blocked 或 not-run。

命名验收、自然语言选路、加载后的工程能力是三种结果。名称解析通过不证明工程效果，过去的作者演练也不证明改名后可正确安装。

现有用例 ID（如 `design-requirements`、`debug-wrong-theory`、`review-code-regression`）保留为稳定标识；当前入口以用例的 `skill` 字段为准。历史作者演练文件和日志保持原样，不冒充新名字下的运行结果。

## 盲评和迭代

比较时隐藏作者和条件标签，用同一任务、相同评分标准评估产物与必要执行证据。先判断正确性、边界和完成度，再看篇幅与表达。允许平局，不用外观整齐抵消语义错误。

高影响用例应重复运行观察波动；计入无谓调查、反复询问和不必要副产物。为修订后的版本另外准备从未用于调参的题目。由于当前题目已在编写过程中对作者可见，不能重新标记为独立留出集。

报告逐项结果和受限结论，不发布没有样本基础的“全面超越”或“能力无损”。不能隔离时保留作者演练结果，明确尚未得到比较性证据。
