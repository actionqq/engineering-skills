# v0.2 Frontend Method Family

v0.2 treats frontend prototype, frontend implementation, and frontend review as three delivery profiles over one design-method family.

## Organization chosen for this revision

The organization is judged by task selection, useful instruction depth, context loaded for a real request, standalone completeness, and maintenance cost. The number of entrypoints, document length, and physical duplication are not quality measures by themselves.

| Approach | Assessment |
|---|---|
| Separate frontend implementation and review entrypoints | Not selected now: mixed frontend/backend changes still need one coherent implementation or review outcome; another entry adds selection overlap without a demonstrated separate workflow. |
| One complete frontend manual copied into every consumer | Not selected: independent distribution does not require identical reading scope, and implementation or review rarely needs the entire exploration method. |
| Central method source with generated per-Skill copies | Deferred: the current references have different purposes and are not byte-identical copies. A build/sync layer would add maintenance without resolving a demonstrated consistency failure. |
| Task entrypoints with substantive workflows and conditional local references | Selected: preserves coherent task execution, relevant specialist depth, and standalone distribution with the existing tooling. |

`SKILL.md` owns the trigger boundary, common workflow decisions, authorization, evidence standards, reference selection, and completion. A reference owns a method substantial enough to be useful only for some invocations. Do not turn an entry into a list of links with no execution guidance, or move a necessary common rule merely to reduce its word count.

The ten current entries distinguish decisions (`tech-design`), evidence (`research`), frontend exploration (`frontend-prototype`), delivery organization (`work-plan`), implementation/tests (`implement`), causal investigation (`diagnose`), assessment (`tech-review`), continuation (`handover`), document disposition (`doc-archive`), and Skill authoring (`skill-dev`). These are task boundaries, not required consecutive phases. Each can use necessary local methods without handing the user through a pipeline.

Reference filenames are local to their Skill. Two files named `frontend.md` can legitimately describe different work. Shared principles must be compatible, but role-specific instructions need not have identical wording or coverage. Only actual copies of the same resource require content equality; a future common source is justified if stable duplicated material and recurring drift make its maintenance benefit concrete.

Project choices such as a selected drawer, palette, or breakpoint are read from current project artifacts. They are not hardcoded into reusable Skill rules. Clear implementation requests may resolve ordinary design details directly; neither a complete prior design nor a separate prototype is mandatory.

These are the rationale and bounded choices applied to this source revision, not a claim that the alternatives have been outperformed in model evaluations.

## Shared method

The common method covers:

- product-vs-brand register;
- information hierarchy, layout, spacing, typography, color, and design-system continuity;
- anti-template / anti-slop heuristics;
- flows, forms, overlays, feedback, and complete UI states;
- keyboard/focus, baseline accessibility, responsive behavior, and content quality.

The method was synthesized from the pinned entry files of Anthropic frontend-design, pbakaus/impeccable, nextlevelbuilder/ui-ux-pro-max-skill, tasteskill/tasteskill, Vercel web-interface-guidelines, and the existing Matt Pocock-derived prototype material. This is not a complete study of their reference trees, scripts, or databases. Each delivery profile carries its own local references and applicable notices so a copied Skill has no runtime dependency on another Skill.

## Delivery profiles

### frontend-prototype

Explores unresolved frontend experience with runnable artifacts. Settled business rules and technical design are inputs. Backend behavior may be stubbed when it is not the subject of the prototype. Completion is evidence about interaction and visual direction, not production readiness.

### implement

Uses the same design principles only when the requested change has a frontend surface. Its responsibility is production integration: real project architecture, real data boundaries, maintainable components, tests, performance and compatibility appropriate to the product. It must not restart open-ended visual exploration when an accepted design or prototype already exists.

An unspecified local visual decision is still implementation work when it can be resolved coherently within the request. New surfaces receive deliberate layout, typography, spacing, and color decisions; established surfaces preserve their accepted direction. Verification follows the changed behavior and risk rather than expanding every small edit into a whole-product audit.

### tech-review

Uses a frontend review lens only when the target contains user-facing UI. It checks implementation against the governing design, project conventions, interaction states, accessibility/responsive basics, and visible product quality. It remains evidence-oriented and read-only by default.

Additional lenses follow the affected behavior and evidence. A small visual refinement does not automatically trigger architecture, data, and full accessibility audits, while a shared interaction component may require wider consumer checks. Necessary common review rules remain in the entrypoint.

## Removed v0.1 overlap

The old generic prototype entry also covered business state modeling and engineering experiments. In v0.2:

- business behavior and state semantics stay with tech-design;
- standalone technical experiments are handled by research with its local experiments reference; probes needed inside design, implementation, or diagnosis remain part of those tasks;
- the user-facing prototype entry is explicitly frontend-focused.

This keeps user entrypoints task-oriented while preventing implement and tech-review from becoming encyclopedic frontend Skills.

## v0.2 review corrections

The frontend split preserves generic task continuation, prerequisite checks, document consistency review, and existing authorization boundaries. Browser/rendered evidence is distinguished from static or build checks. Production delivery does not require first creating a prototype.

The active case bank excludes the retired prototype capability. Original cases remain in `evals/retired-cases.json` for historical reproducibility; the author runner explicitly labels its SQLite case as historical. No new frontend model evaluation has been prepared or claimed. The method map restores dependency fidelity and retains technical experiment depth under research.
