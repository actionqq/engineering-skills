## Cross-skill findings

1. **Verification discipline was present but too implicit.** The implement entry asked for proportionate checks and accurate reporting, but did not give a compact evidence-to-claim mapping. Added a conditional verification reference. It does not mandate full suites for every edit.
2. **Security review had no explicit risk lens.** General code review could catch security issues, but lacked a prompt to trace trust boundaries, object/tenant authorization, secrets, and exploit variants. Added a conditional lens rather than a standalone security-audit skill. Specialist audits remain out of scope.
3. **Test-strengthening techniques were under-signaled.** Mutation testing and property-based testing are useful when ordinary examples do not establish the oracle or input-space behavior. They are now mentioned as optional techniques, not default dependencies.
4. **Frontend ecosystem guidance should remain version-aware.** Vercel's rule catalogs are framework-specific and frequently updated. Do not copy an entire React/Next.js catalog into a generic frontend reference; load the matching source only when the project uses that stack, and record the revision used for a consequential review.
5. **Workflow completeness does not justify workflow rigidity.** Superpowers and SDD frameworks offer useful methods, but fixed stage gates, agent counts, retry thresholds, and automatic branch actions conflict with the existing user-directed execution model. Keep their useful reasoning, reject their absolute orchestration rules.

## Deferred candidates and why

- Dedicated security audit / smart-contract / language-specific audit Skills: valuable in their domains, but their scanners, harnesses, expertise and threat models are not generic. A risk lens is appropriate here; import a specialist package only for a matching project.
- Mutation-testing and post-patch-validation executors: the upstream tools provide much more than a prompt. Do not claim their differential isolation or evidence guarantees from prose alone. Revisit if the repository gains a reproducible runner and a real use case.
- React/Next.js rule catalogs: high value for matching projects, but not a universal frontend standard. Avoid freezing a fast-changing catalog into the bundle.
- Git worktree / branch-finishing / auto-commit workflows: these are harness and user-policy dependent. No automatic commit, push, merge, or cleanup.
- New standalone testing, security, debugging, or frontend-review entries: current entry ownership remains adequate; use conditional references until real request patterns prove a distinct entrypoint is needed.

## Limitations and follow-up

The source inspection covered the named Skill entry files and repository trees, not every nested rule, script, plugin workflow, evaluation, or license file. The two added references are original synthesis, not copied upstream text. Their behavior has not been independently model-evaluated or installed across hosts. Before adopting any source text or executable assets, inspect its exact license and preserve required notices. Next useful evaluation: compare the same realistic implementation and review prompts with/without the new references, checking for evidence-backed claims, security boundary coverage, and no unnecessary workflow expansion.
